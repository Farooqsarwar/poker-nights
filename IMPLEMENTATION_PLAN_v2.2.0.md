# PART 0 — THREE HAZARDS. READ BEFORE WRITING ANY CODE.

## Hazard 1 — `TournamentStructure` carries no engine version

`lib\models\tournament.dart:472-494` — the constructor has 20 parameters and **none of
them is a version**.

`lib\utils\structure_verification.dart:78` `StructureVerification.audit()` re-runs
`TournamentEngine.generate()` against the game's own settings and compares blinds level
by level (`:163-179`). It has no way to know which engine produced the stored structure.

**Consequence:** the moment you change the growth curve (Phase 3), every structure ever
generated by the 2.1.0 engine — completed games, running games, scheduled games —
recomputes differently and is reported to players as
`"Level 4 is 100/200; these settings produce 150/300."` The app will accuse every honest
host in the install base of tampering.

This is not theoretical. `audit()` is called on player devices, not just the host's.

**Fix in Phase 1. Non-negotiable. Nothing else ships first.**

`lib\utils\model_codec.dart:195-214` — `tournamentStructureToMap()` writes 18 keys.

## PHASE 3 — Risk-adjusted growth (#3). The hard one.

**Prerequisite: Phase 1 must be merged and deployed.** Without the version guard this
change reports every existing game as tampered.

### 3.1 Read this before you touch the loop

The spec's §11.3 says `BBᵢ = snapToPracticalBlind(...)`. **The code does not work that
way and you should not make it.**

`lib\utils\tournament_engine.dart:1745-1780` walks a **cursor** over the
`validBlindLevels` ladder:

```dart
    final ladder = [...validBlindLevels];     // :1745
    var cursor = startIndex;                  // :1747
    var prevBB = openingBB;                   // :1748

    for (var i = 0; i < numLevels; i++) {
      if (i == 0) { /* opening level, verbatim */ }
      else {
        final raw = openingBB * math.pow(growthFactor, i);         // :1757

        // extend the printed ladder in +200 steps for huge fields
        if (cursor >= ladder.length - 1 && raw > prevBB) { ... }   // :1760-1763

        // guarantee strict monotonicity even when growth is nearly flat
        while (cursor < ladder.length - 1 && ladder[cursor][1] <= prevBB) {
          cursor++;                                                // :1767-1769
        }
        // track the raw curve: advance while the next rung is nearer
        while (cursor < ladder.length - 1 &&
            ladder[cursor + 1][1] > prevBB &&
            (ladder[cursor + 1][1] - raw).abs() < (raw - ladder[cursor][1]).abs()) {
          cursor++;                                                // :1772-1777
        }
      }
    }
```

`snapToPracticalBlind` (`:162`) is used for **individual antes only** (`:1792`), the
live speed-up/slow-down edits (`app_provider_tournament.dart:330, :331, :375, :376`)
and the level-extension proposal (`app_provider_timer.dart:567, :573, :578`).

**Keep the cursor walk exactly as it is.** Change only the value of `raw` it chases.
The monotonicity guarantee and the ladder extension are load-bearing and the spec's
formulation has neither.

### 3.2 Resolve the spec's circular dependency first

§10 orders generation as: growth curve = **step 5**, rebuy-close optimisation =
**step 9**. But `rebuyPremium(i)` needs `closeLevel`, and the optimiser needs the
finished curve.

In the code the optimisation happens at
`lib\utils\tournament_engine.dart:1904, :1920, :1926, :1951` — **after** the loop.

**Decision: use `params.rebuysCloseLevel` — the requested value — for the premium.**
Rationale: the premium models *the host's plan* for when chips stop entering, and the
host's plan is what they typed. Using the optimised value would make the curve depend
on a number the host never saw, and `rebuyCloseChosenByOrganizer`
(`tournament.dart:194-201`) already establishes that an explicit choice is
authoritative.

**Document this as §39 deviation 17.**

### 3.3 The change

Replace `lib\utils\tournament_engine.dart:1738-1743` entirely:

```dart
    // ── Risk-adjusted growth (§11.3) ────────────────────────────────────────
    // Chips that enter after level 1 — rebuys, re-entries — are chips the
    // blind curve must eventually outrun. A curve solved only from the total
    // ends up too shallow early and too steep late. The premium front-loads
    // the growth into the window where those chips are actually arriving, and
    // `gBase` is solved DOWN so the ladder still lands on targetFinalBB at the
    // planned finish rather than overshooting by the premium's product.
    final premiumCloseLevel = params.rebuysCloseLevel;
    final maxPremium = params.effectiveFormat.hasLateChips && params.buyIn > 0
        ? (0.30 * (1 - params.effectiveRebuyCost / params.buyIn))
            .clamp(0.05, 0.25)
            .toDouble()
        : 0.0;

    // Level is 1-based here, matching the spec. Zero once rebuys have closed.
    double rebuyPremium(int level) =>
        (maxPremium == 0 || level > premiumCloseLevel || premiumCloseLevel <= 0)
            ? 0.0
            : maxPremium * (premiumCloseLevel - level + 1) / premiumCloseLevel;

    // The compounded effect of every premium the ladder will apply. Solving
    // gBase against this is what keeps the finish on target.
    var premiumGrowthFactor = 1.0;
    for (var l = 2; l <= premiumCloseLevel && l <= plannedLevels; l++) {
      premiumGrowthFactor *= 1 + rebuyPremium(l);
    }

    final gBase = math
        .pow(
          math.max(targetFinalBB, openingBB.toDouble()) /
              (openingBB * premiumGrowthFactor),
          1 / math.max(1, plannedLevels - 1),
        )
        .toDouble();
```

Then in the loop, **replace line `:1757`**:

```dart
        final raw = openingBB * math.pow(growthFactor, i);
```

with a running cumulative product — `math.pow` no longer works because the rate now
varies per level. Declare the accumulator next to `prevBB` at `:1748`:

```dart
    var rawCurve = openingBB.toDouble();
```

and inside the `else` branch, as its first statement:

```dart

        // i+1, so the first multiplication (i == 1) must use rebuyPremium(2).
        rawCurve *= gBase * (1 + rebuyPremium(i + 1));
        final raw = rawCurve;
```

### 3.4 The off-by-one — the single most likely defect

The product in §11.3 runs `k = 2..closeLevel`. The loop's `i` is 0-based.

| Loop `i` | Spec level | Premium applied | Times multiplied so far |
|---|---|---|---|
| 0 | 1 | none (opening level, verbatim) | 0 |
| 1 | 2 | `rebuyPremium(2)` | 1 |
| 2 | 3 | `rebuyPremium(3)` | 2 |
| … | … | … | … |
| `n-1` | `n` | `rebuyPremium(n)` | `n-1` |

So `premiumGrowthFactor` must be `∏(k=2..closeLevel) (1 + rebuyPremium(k))` — the loop
above starts at `l = 2`, which is correct. Get either bound wrong and the ladder misses
`targetFinalBB` by the premium's product, which at `maxPremium = 0.20` and
`closeLevel = 6` is **60%**.

### 3.5 Verification test — the spec's own worked example

```dart
test('§11.3 worked example: the raw curve lands on target', () {
  const openingBB = 4;
  const targetFinalBB = 6000.0;
  const plannedLevels = 22;
  const closeLevel = 6;
  const maxPremium = 0.20;

  double premium(int l) =>
      l > closeLevel ? 0.0 : maxPremium * (closeLevel - l + 1) / closeLevel;

  var pgf = 1.0;
  for (var l = 2; l <= closeLevel; l++) {
    pgf *= 1 + premium(l);
  }
  expect(pgf, closeTo(1.603, 0.01));          // spec: ≈ 1.603

  final gBase = math.pow(
    targetFinalBB / (openingBB * pgf), 1 / (plannedLevels - 1)).toDouble();
  expect(gBase, closeTo(1.385, 0.01));        // spec: ≈ 1.385

  var raw = openingBB.toDouble();
  for (var i = 1; i < plannedLevels; i++) {
    raw *= gBase * (1 + premium(i + 1));
  }
  expect(raw, closeTo(targetFinalBB, 1.0));   // lands on 6000 at level 22
});
```

**Assert against the raw curve, before ladder snapping.** Snapping moves the printed
values to legal rungs and the equality will not hold on `levels.last.bb`.

## PHASE 5 — `reserveMultiplier` (#15)

### 5.1 What is actually there

`lib\utils\tournament_engine.dart:427-433` — `_buildChipPlan` takes a
`reserveMultiplier` positional. Call sites:

| Line | Value | Context |
|---|---|---|
| `:376` | `1.0` | `chipPlanAtLevel` fallback |
| `:388` | `1.0` | `chipPlanAtLevel` fallback |
| `:1518` | `1.0` | starting-stack plan |
| `:1812` | `2` | rebuy chip plan |
| `:1819` | `2` | add-on chip plan |

So for the **starting stack** it is dead, and for rebuy/add-on it is an undocumented
magic number.

The real scarcity handling is the divisor-candidate ladder at `:1508-1511`, which tries
progressively less conservative divisors until one funds a legal opening depth.

### 5.2 What to do — and what NOT to do

**Do not delete the ladder.** The spec's formula has no escape hatch; on a small chip
set it will fail to fund any legal depth and the generator will throw where today it
degrades gracefully to a Turbo with a `styleNote` explaining why
(`tournament.dart:505-511`).

**Instead, make the spec's formula the first, most-conservative candidate** and keep the
ladder behind it as the fallback.

Add to `TournamentParams` (`lib\models\tournament.dart`, after `:250`):

```dart
  /// §12.1: how many times over the box must fund one seat's worth of chips.
  /// One for the starting stack, plus the expected extra entries per seat. An
  /// add-on counts half — it is one stack arriving once, late, after colour-up
  /// has already retired the small denominations it would otherwise need.
  double get reserveMultiplier {
    if (players <= 0) return 1;
    return 1 +
        effectiveExpectedRebuys / players +
        effectiveExpectedReEntries / players +
        effectiveExpectedAddOns / players * 0.5;
  }
```

Then at `:1508-1511`, put it at the head of the candidate list. Read the surrounding
20 lines first — the candidates are divisors, and `reserveMultiplier` multiplies a
divisor rather than replacing one. The wiring is:

```dart
// the most conservative candidate first, the existing ones as fallbacks
final candidates = <double>[
  params.players * params.reserveMultiplier,
  ...existingCandidates,
];
```

Replace the literal `2` at `:1812` and `:1819` with a named constant so the number stops
being a mystery:

```dart
  /// A rebuy or add-on box must stretch to roughly two takers per seat before
  /// the host is handing out chips that are already in someone's stack.
  static const double lateEntryReserveMultiplier = 2;
```

- [ ] A deliberately tiny chip set still generates (a warning, not a throw)
